# Wire protocol

How Home Assistant talks to the sensor over Bluetooth LE. Nothing about the
Wi-Fi clients is ever advertised; the advertisement only says "I am a Wi-Fi
presence sensor". Client MACs travel exclusively inside AES-256-GCM messages that
only a holder of the pairing key can produce or open, and the settings can only
be changed by a holder of the key.

All multi-byte numbers are big endian. Reference implementations:
`main/wp_crypto.c`, `main/wp_gatt.c`, `main/wp_config.c`, `main/wp_report.c`
(device) and `custom_components/wifi_presence/protocol.py`, `session.py`
(Home Assistant, shared with `tools/wp_client.py`).

## Pairing key

32 random bytes, **generated by the sensor on its first boot** from the hardware
random generator (after the radio is running, when it is a true entropy source),
stored in its flash and printed on the serial console as 64 hex digits. The user
copies it into Home Assistant once. Erasing the flash creates a new key.

## GATT

| Item | UUID |
|------|------|
| Service | `6e1d0001-5a3c-4f1e-9b7a-0c2d8e4f1a60` |
| CTRL (write) | `6e1d0002-…` |
| DATA (notify) | `6e1d0003-…` |
| CMD (write) | `6e1d0004-…` |

Advertisement: connectable, flags + the 128-bit service UUID; scan response: the
device name. One connection at a time; the device drops a connection after
`WP_CONN_TIMEOUT_S` (20 s).

## Reading the client list

1. Client connects and enables notifications on DATA.
2. Client writes CTRL: `0x01 || client_nonce` (17 bytes, 16 fresh random bytes).
3. Device picks `dev_nonce` (16 bytes, hardware RNG), derives the **session key**

   ```
   key = HMAC-SHA256(PSK, "wifi-presence v1 session" || client_nonce || dev_nonce)
   ```

   and answers on DATA with one message:

   ```
   message = 0x01 || dev_nonce(16) || ciphertext || tag(16)
   AES-256-GCM(key, iv = iv(0, 0), aad = message[0:17], plaintext = report)
   ```

The session key is unique per request (fresh nonces on both sides). A recorded
message cannot be replayed against a later `client_nonce`, and nobody without the
PSK can forge one. The key stays valid for commands until the next CTRL write or
disconnect.

### GCM nonce

12 bytes: `direction(1) || 0x00 × 7 || counter(4)`. Direction 0 = device to
client, 1 = client to device. The report uses counter 0; commands and their
acknowledgements use the command's counter. A (key, direction, counter) triple is
never used twice.

### Fragmentation

A message is split into chunks of at most `ATT_MTU - 3` bytes (notifications) or
`min(MTU - 3, 244)` bytes (writes). Each chunk is `hdr || data`: `hdr` bit 7 marks
the last fragment, bits 0-6 are the sequence number from 0 (at most 128 fragments).
Gaps or overflow make the receiver drop the message.

## Report (plaintext)

```
u8   version = 2
u8   flags       bit0: client list truncated
u32  uptime_s
u8   ap_count    access point BSSIDs currently watched
u32  config_crc  CRC-32 of the settings blob in force, 0 = none stored yet
u8   n
n x  { u8[6] mac, i8 rssi, u16 age_s }
```

`age_s` = seconds since the client's last frame (saturates at 65535). A client is
listed once it passed the sensor's `min_frames` / `hold_s` rules.

## Commands (client to device)

After a report, the client may send commands on CMD, in the same session:

```
message = 0x01 || counter(4) || ciphertext || tag(16)
AES-256-GCM(key, iv = iv(1, counter), aad = message[0:5], plaintext = command || payload)
```

`counter` starts at 1 and must increase with every command in the session.

- A command that does not authenticate, or whose counter is not higher than the
  last accepted one, is dropped **without any answer**: an attacker learns nothing.
- A write that arrives with no session (no report requested on this connection),
  without notifications enabled, while another request is being handled, with a
  wrong fragment sequence, or larger than 244 bytes is refused with an ATT error.

| Command | Payload | Effect |
|---------|---------|--------|
| `0x01` SET_CONFIG | settings blob | validate, store in flash, apply immediately |

Acknowledgement on DATA, sealed under the same key with `iv(0, counter)`:

```
message = 0x01 || counter(4) || ciphertext || tag(16)      aad = message[0:5]
plaintext = 0xA1 || status(1) || config_crc(4)
```

`status`: 0 OK, 1 invalid (does not parse, out of range, unknown command),
2 flash error. `config_crc` is the CRC of the settings now in force; the client
checks it against the blob it sent. A successful SET_CONFIG is also what marks the
sensor as *paired* (it then stops repeating the key on the console).

Sending identical settings is accepted without a flash write or a rescan.

## Settings blob

```
u8   version = 1
u8   band            0 both, 1 2.4 GHz only, 2 5 GHz only
char country[2]      "DE": upper-case ASCII
u16  scan_dwell_ms   120..1500   passive AP search, per channel
u16  hop_ms          200..30000  listening per channel while sniffing
u16  rescan_s        30..3600    between AP searches
u8   min_frames      1..100      frames before a client counts as present
u16  hold_s          10..43200   a client stays present this long after its last frame
i8   min_rssi        -100..-20   frames weaker than this (dBm) are ignored
u8   n_ssids         0..8
n x  { u8 len (1..32), bytes ssid }     no NUL bytes
```

The blob is strict: no trailing bytes, every field range-checked. `config_crc` is
the standard CRC-32 (zlib) of the blob exactly as stored, so Home Assistant and the
sensor agree on "same settings" byte for byte. The integration sends the settings
with every poll that finds a different CRC, which also restores a sensor that was
erased.
